# Bodega data dictionary

This dictionary describes the PostgreSQL schema after migrations `001_data_state.sql` through
`006_sales_records_final_shape.sql`. It was taken from `information_schema` on a freshly migrated
database. It follows the final Milestone 3 ERD (Diagram 5) and sections 7.1–7.4. Where the
physical design differs from the ERD, the difference is listed in section 6.

The single owner is seeded by `migrate()` from `OWNER_ID` and `OWNER_DISPLAY_NAME`. Every row is
owner-scoped through `owners`. Enumerations are `text` with a `CHECK`, not PostgreSQL enums
(M3 section 10).

## 1. owners

| Column | Type | Null | Default | Rules |
|---|---|---|---|---|
| id | uuid | no | | Primary key. From `OWNER_ID`. |
| display_name | varchar(100) | no | `'Owner'` | From `OWNER_DISPLAY_NAME`. |
| created_at | timestamptz | no | now() | |

Deleting an owner cascades to its submissions, sales records and baseline snapshots.

## 2. submissions — one capture attempt

| Column | Type | Null | Default | Rules |
|---|---|---|---|---|
| id | uuid | no | | Primary key. Generated by the server, or by the client for standalone manual entry (UUID v4, once per form). |
| owner_id | uuid | no | | FK → owners, `ON DELETE CASCADE`. Immutable. |
| input_type | text | no | `'TEXT'` | `IMAGE`, `TEXT` or `MANUAL`. Immutable. |
| status | text | no | `'UPLOADED'` | `UPLOADED`, `CLASSIFYING`, `NEEDS_VERIFICATION`, `AI_UNAVAILABLE`, `REJECTED` or `CONFIRMED`; transitions are in section 5. |
| sale_date | date | no | | Not in the future (the API uses the `APP_TIMEZONE` business date; the database allows 1 day of skew). Immutable. |
| image_key | text | yes | | Random `images/{uuid4}.jpg` key of the sanitized image in the private bucket. Cleared by the 30-day purge. |
| masked_text | text | yes | | Typed text after phone/email masking, at most 5,000 characters. Raw text is never stored. Cleared by the 30-day purge. |
| draft_payload | jsonb | yes | | Masked draft: `{version, message, lines[{lineId, itemName, quantity, unitPrice, bands}]}` (M3 7.3). Must be null once CONFIRMED. |
| created_at | timestamptz | no | now() | The 30-day retention clock. |
| updated_at | timestamptz | no | now() | Set by the trigger on every update. The 120-second stale-sweep clock. |
| confirmed_at | timestamptz | yes | | Set by the trigger on confirmation; required when CONFIRMED. |

- Unique `(id, sale_date)`, which the composite sales FK references.
- Indexes: `(owner_id, status, sale_date)`, `(status, updated_at)` for the stale sweep,
  `(created_at)` for the purge.

## 3. sales_records — confirmed rows only (final ERD shape since 006)

| Column | Type | Null | Rules |
|---|---|---|---|
| id | uuid | no | Primary key; returned as `recordId`. |
| submission_id | uuid | no | FK → submissions, `ON DELETE CASCADE`. |
| line_no | integer | no | 1–100, unique per submission (`lineNo`). |
| item_name | text | no | 1–100 characters after trimming, at least one non-space character. |
| item_key | text | no | Generated: `lower(btrim(item_name))`, indexed (M3 7.2 index on itemKey). |
| quantity | numeric | no | Greater than 0, at most 99,999.99, at most 2 decimal places (FR-202 as clarified in M3 section 3). |
| unit_price | numeric | no | At least 0, at most 9,999,999.99, at most 2 decimal places. |
| source | text | no | `AI_EXTRACTED` (an AI row, even if the owner corrected it) or `MANUAL`. |

- **No sale date on the row** (M3 7.1). Every read takes it from the parent submission.
  Migration 006 dropped the old copy. The composite FK it replaced had always forced it to equal
  the parent's date, so no information was lost.
- Rows are immutable: an `UPDATE` trigger rejects every edit. 006 renumbered `line_no` under a
  temporary trigger disable, in order, with no value changes.
- A CONFIRMED submission has 1–100 rows; every other status has none. Deferred constraint
  triggers check this at commit.
- `lineTotal = quantity × unit_price` is computed in the API and never stored.
- The 005 limits are `NOT VALID`: PostgreSQL enforces them on every new or updated row, while
  rows written before 005 stay readable and unchanged.

## 4. baseline_estimates — analysis snapshots (SD-03 saveBaselines)

| Column | Type | Null | Rules |
|---|---|---|---|
| id | uuid | no | Primary key. |
| owner_id | uuid | no | FK → owners, `ON DELETE CASCADE`. |
| as_of_date | date | yes* | Analysis date. *Required for every new row; legacy pre-005 rows may be null and are never "latest". |
| item_key | text | yes* | Trimmed, case-folded item name. *Required for every new row. |
| item_name | text | no | Display label (the most recent spelling), 1–100 characters. |
| window_days | integer | no | 7. |
| cover_days | integer | no | Always 7. |
| logged_days | integer | no | Logged dates in the 28-day window. |
| average_daily_quantity | numeric | no | Latest 7-logged-day average, at least 0. |
| prior_average_daily_quantity | numeric | yes | Previous 7-logged-day average; null without 14 logged dates. |
| trend | text | no | `UP`, `DOWN`, `STABLE` or `INSUFFICIENT_DATA`. |
| suggested_restock_qty | integer | no | `ceil(average × 7)`, at least 0. |
| computed_at | timestamptz | no | |

- Unique `(owner_id, as_of_date, item_key)`: every analysis run replaces that date's snapshot.
- Snapshots are an audit record only. Responses are always recomputed from confirmed sales, so a
  stale snapshot can never be shown.
- Deleted 30 days after `as_of_date`, and for the whole owner whenever any submission is deleted.

## 5. image_deletion_jobs — outbox for image cleanup (M3 7.4)

| Column | Type | Null | Rules |
|---|---|---|---|
| image_key | text | no | Primary key. Queued in the same transaction that removes the reference. |
| created_at | timestamptz | no | |
| attempt_count | integer | no | Increased on each failed storage delete. |
| last_attempt_at | timestamptz | yes | |

There is no foreign key, so the job outlives the submission. The object is deleted after the
transaction commits. A failure stays queued and is retried by the retention sweep.

## 6. Lifecycle (M3 Diagram 4, enforced by the `submission_transition` trigger)

```text
insert -> UPLOADED                      (photo or text)
insert -> CONFIRMED                     (standalone manual entry, input_type MANUAL only)
UPLOADED -> CLASSIFYING | AI_UNAVAILABLE (stale > 120 s)
CLASSIFYING -> NEEDS_VERIFICATION | REJECTED | AI_UNAVAILABLE
NEEDS_VERIFICATION | AI_UNAVAILABLE | REJECTED -> CONFIRMED   (one transaction with its rows)
open state -> deleted                   (owner discard, or 30-day purge)
CONFIRMED -> deleted                    (owner deletes the submission)
```

The same-state updates are allowed. Every other pair fails with `23514`, and all 36 state pairs
are tested in `tests/test_final_contract.py`. A late extraction result can never overwrite an
outcome already recorded, because the final write is guarded by `expected_status='CLASSIFYING'`.

## 7. Differences from the ERD, and why

| ERD (M3 7.1–7.2) | Physical design | Reason |
|---|---|---|
| `CHECK (inputType = 'IMAGE') = (imageKey IS NOT NULL)` | Enforced in code (as M3 7.2 allows) | The purge nulls `image_key` on confirmed image submissions. |

SQLAlchemy models (`app/models.py`) and Alembic migrations (`backend/alembic`) are in place and checked against each other (D-18). Since migration 006, the earlier differences (a repeated `sale_date`, 0-based line numbers, and no
`itemKey` column) no longer apply.
